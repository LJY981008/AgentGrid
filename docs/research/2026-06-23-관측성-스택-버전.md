## 핵심 결정포인트 (실측)

1. **FastAPI 통합 = instrumentator 8.x**(raw `make_asgi_app` 아님). `Instrumentator().instrument(app).expose(app)` 한 줄로 `http_request_duration_seconds`(Histogram)·`http_requests_total` 자동. raw는 HTTP 미들웨어 직접 구현 필요.
2. **배치(25분)는 pull로 못 잡음** → **Pushgateway 필수**(종료 시 프로세스 소멸·scrape 불가). `push_to_gateway(grouping_key={round})` 로 라운드 영속.
3. **peak 메모리 = Prometheus RSS Gauge 불가**(① scrape 순간값이라 peak 놓침 ② 할당 코드 줄 모름) → **tracemalloc(Python 힙 peak) + RSS(ru_maxrss) 대조** + memray(할당 줄). ⚠️ tracemalloc/memray는 **Python 힙만** — DuckDB C++ 버퍼면 RSS≫tracemalloc 로만 드러남.
4. **라이브 곡선**: profiler가 `start_http_server`로 `/metrics` 노출 → Prometheus scrape마다 `process_resident_memory_bytes`(ProcessCollector 자동)=RSS 곡선 + 커스텀 collector(라이브 PhaseTimer)=phase 진행. Pushgateway는 last-value-per-group이라 곡선 부적합 → 곡선은 scrape가 맡음.
5. **Grafana Local Snapshot**(네이티브) = 데이터 동결 정적 대시보드 → 최적화 before/after 2장 비교. grafana.db(SQLite·`/var/lib/grafana`) 저장 → **grafana-data 볼륨 영속 필수**.
6. **레이어 대시보드 모델**(tbbe-hub 참조): L1 신호등(overview·traffic-light)→drill-down(외부의존·파이프라인·무결성)+인프라(호스트·DB). 폴더/태그 분류.

## 과투자 경계

상시 FastAPI엔 Prometheus+Grafana 적정, **1회 배치엔 다소 과함**(pull 부적합+peak 못잡음). 1인 로컬: 핵심 레이어(L1/L3/호스트)부터·exporter(PG·node) 후속. 사용자가 Grafana 대시보드+스냅샷 명시 요구 → 정당.

## caveat (미확인·실사용 검증)

- snapshot이 raw 전체 시리즈 보존 vs 렌더 패널 데이터만인지는 패널 구성 의존(실사용 검증).
- 호스트 9090/3000 점유 가능(현 프로젝트 5433/5174 리맵 전례 → 실측: **3000 점유→grafana 3001**·9090/9091 비점유).
