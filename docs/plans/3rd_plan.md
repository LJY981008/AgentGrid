## 1. 결정 기록 (2026-06-12 사용자 확정 — 변경 금지)

### 1.1 결정 #1 — 가중치·경계값 확정 프로세스: 시드 캘리브레이션 1회 후 동결

**결정**: 2nd_plan §4.2 가중치·§4.4 등급 경계값 초안은 **M3 착수 전 시드 캘리브레이션 1회**를 거쳐 동결한다.
1. 시드 repo 15~20개 선정 — 품질이 알려진 **앵커 repo**(공식 SDK 예제급 상위 품질 + 알려진 저품질) 포함.
2. 규칙 분석기로 축별 점수 산출 → 초안 합산식 적용 → **등급 분포 검토 (목표: A 등급 10~20%)**.
3. 분포가 목표를 벗어나면 가중치/경계값 조정 → 재검토 (필요 시 수회 반복, 단 시드 집합은 고정).
4. **동결 + 분석기 버전 태그** 부여. 이후 변경은 분석기 버전 증가로만 가능 (가드레일 #3 의 버저닝 체계와 동일 메커니즘).
5. **최종 승인 주체 = 사용자(프로덕트 오너)**.

**근거**: 가중치를 책상 위에서 확정하면 "전부 A" 또는 "전부 F" 분포로 변별력을 잃을 위험. 실측 분포 기반 1회 조정이 최소 비용으로 변별력을 확보한다. 반복 캘리브레이션(상시 조정)은 등급의 시점 간 비교 가능성을 깨뜨리므로 1회 후 동결.

**트레이드오프 (수용함)**: 시드 15~20개는 통계적으로 작은 표본 — 초기 분포가 모집단을 대표하지 못할 수 있음. 분석기 버전 태그 체계가 있으므로 추후 대규모 데이터 확보 시 v2 캘리브레이션으로 보완 가능.

**구현 함의**:
- 등급 레코드에 **분석기 버전 필드 필수** (가드레일 #3 의 프롬프트/모델 버전과 함께 3종 버전 기록) — db-architect 전달 사항.
- 캘리브레이션 시점(M3 착수 전)에는 **TS 분석기만 존재**(M2 산출물) → 시드는 TS 중심으로 구성하고, 합산식은 코드 구현 전 축 점수에 수식을 오프라인 적용해 분포를 검토한다. Python 앵커 2~3개는 M3 중반(파이썬 분석기 완성 후) **스폿 체크**로 동결값 유효성을 확인한다. 스폿 체크 불일치 시 처리는 신규 미해결 질문 #9.
- 시드 제출은 운영자(사용자)가 직접 수행 — 2nd_plan 확정 결정 #2(수동 등록)의 "시드 데이터 운영자 제출" 항목을 M4 에서 M2 완료 직후로 앞당기는 효과 (§2 마일스톤 영향 참조).

### 1.2 결정 #2 — LLM 보정 모델: claude-sonnet-4-6 + 예산 체계

**결정**:
- **모델 = claude-sonnet-4-6** ($3 입력 / $15 출력 per MTok, 1M 컨텍스트 — 2026-06 공식 단가).
- **입력 구성**: 규칙 엔진이 검출한 호출지점(call site) ± 주변 코드 발췌 + README/매니페스트. 통상 50~100K 토큰 수준, **입력 200K 토큰 cap** (초과분은 발췌 우선순위 컷 — 우선순위 산정 방식은 backend-expert 협업 지점).
- **구조화 출력(JSON Schema)** 로 파일/라인 인용 근거를 강제 — 가드레일 #4(근거 강제)의 구현 수단.
- **건당 예상 비용 $0.2~0.4**. **월 예산 상한 초기 $30** (운영 설정값으로 조정 가능). 예산 초과 시 가드레일 #6 발동 — 규칙 점수만으로 등급 산출 + "LLM 보정 미적용" 라벨.
- 등급 레코드에 **모델 버전 기록** → 추후 Opus 4.8 등 상위 모델 승격 시 구버전 분석 라벨링(가드레일 #3)으로 자연 전환.

**근거**: 보정 역할(±10점, 최대 1등급)에는 최상위 모델이 불필요. sonnet-4-6 은 1M 컨텍스트로 대형 repo 발췌도 단일 호출로 처리 가능하며, 건당 $0.2~0.4 는 1인 운영 예산에서 지속 가능. 전체 repo 를 넣지 않고 규칙 엔진 검출 지점 중심 발췌를 쓰는 것은 비용 절감과 동시에 LLM 의 주의를 보정 대상에 집중시키는 효과.

**트레이드오프 (수용함)**: 발췌 기반 입력은 발췌 밖 컨텍스트를 놓칠 수 있음 — 보정 폭이 ±10 으로 제한되어 있어 오판 영향이 구조적으로 캡핑됨. 월 $30 은 보정 가능 건수를 약 75~150건으로 제한 — 초과분은 규칙 전용 등급으로 서비스 성립(2nd_plan §6 의 LLM=Should 논리와 정합).

**구현 함의**:
- 월 예산 카운터(누적 비용 집계)와 예산 설정값 저장 구조 필요 — db-architect 전달 사항.
- LLM 결과 캐시 키 = (commit hash, 분석기 버전, 프롬프트 버전, 모델 ID) 4-튜플 (가드레일 #2) — 캐시 테이블 설계에 반영.
- 예산 소진으로 미보정된 건의 소급 보정 여부는 신규 미해결 질문 #10.

### 1.3 결정 #3 — 분석 격리: 2단계 점진 도입

**결정**:
- **1단계 (M1~M2): 안전 취득 규칙** — shallow clone(`--depth 1`), repo 크기/파일 수 상한, symlink 무시, 경로 검증(traversal 차단). 클론한 코드는 절대 실행하지 않음(2nd_plan F2 비실행 원칙 계승).
- **2단계 (M2 내): 분석 워커 별도 컨테이너 분리** — 읽기전용 FS(클론 볼륨 제외), 네트워크 차단(클론 단계 제외), CPU/메모리 리소스 limit.

**근거**: 정적 분석이라도 신뢰 불가 repo 클론·파싱 자체에 위험(거대 파일, symlink 탈출, 압축 폭탄류, 파서 DoS)이 있음. 1단계는 코드 레벨 방어로 즉시 적용 가능하고, 2단계는 기존 compose 기반 인프라라 **증분 비용이 낮음** — VM/gVisor 급 격리는 1인 운영 과잉으로 판단.

**트레이드오프 (수용함)**: 컨테이너 격리는 커널 공유 한계가 있으나, 코드 비실행 원칙 하에서 잔여 위협은 파서 취약점 수준 — 리소스 limit + 비실행으로 충분히 완화. M1 기간(통짜 관통 단계)은 1단계 방어만으로 운영 — 이 기간 제출은 운영자 시드뿐이므로 위험 노출 낮음.

**구현 함의**:
- 상한 수치(repo 크기, 파일 수, clone 타임아웃)는 **운영 설정값**으로 외부화 — backend-expert 협업 지점.
- 워커 컨테이너 분리는 compose 서비스 추가 + 보안 옵션(read_only, network mode 등) — devops-engineer 협업 지점. 위협 모델 검토는 security-reviewer 위임.

### 1.4 결정 #6 — 어뷰징 방지: rate limit 체계, CAPTCHA 없음

**결정**: 3중 방어, 전부 **운영 설정값**으로 수치 조정 가능하게 설계.

| 계층 | 초기 설정값 (제안 수치) | 비고 |
|---|---|---|
| IP 기반 rate limit | 제출 IP당 시간당 5건 / 일 10건 | 429 응답 + 재시도 가능 시각 안내 |
| 전역 일일 제출 상한 | 일 50건 | 분석 파이프라인·LLM 예산 보호. 초과 시 "오늘 접수 마감" 안내 |
| 악성 repo 신고 | 수동 채널 — 이메일 / GitHub Issue | 상세 페이지·제출 폼에 링크 노출. 처리(게시 중단)는 운영자 수동 |

**근거**: 비로그인 제출 폼의 어뷰징 표면은 "대량 제출로 파이프라인/LLM 예산 고갈"이 핵심 — CAPTCHA 는 정상 개발자 UX 를 해치면서 표적 공격은 못 막음. rate limit + 전역 상한이 비용 측면 피해를 구조적으로 캡핑하고, 악성 콘텐츠는 초기 볼륨에서 수동 신고로 충분.

**트레이드오프 (수용함)**: 분산 IP 공격(봇넷)은 전역 상한에 걸려 정상 사용자 제출까지 막힐 수 있음 — 초기 트래픽 규모에서 발생 확률 낮고, 발생 시 운영 설정값 조정으로 대응. CAPTCHA 부재로 단순 스크립트 제출은 가능하나 전역 상한이 최종 방어선.

**구현 함의**:
- 전역 일 50건 상한 ↔ LLM 월 예산 $30(보정 75~150건)의 **상호작용**: 상한까지 꽉 차면 월 최대 1,500건으로 LLM 예산을 초과하지만, 가드레일 #6(미적용 라벨)이 안전판이므로 정합 — 두 수치는 독립 조정 가능.
- rate limit 카운터는 Redis 기반이 자연스러우나 구현 선택은 backend-expert 영역. 설정값 외부화 구조는 결정 #3 상한 수치와 공통 패턴.

### 1.5 결정 #8 — MVP 프론트엔드: 풀 4화면

**결정**: **디렉토리(목록/검색/필터) / 도구 상세 / 제출 폼 / 제출 상태 추적** 4화면 전부 MVP 범위. M4 내 구현 우선순위는 **디렉토리 → 상세 → 제출(+상태 추적)**. 일정 촉박 시 **뒤쪽부터 축소** (제출/상태는 임시로 API 직접 호출 안내로 대체 가능). frontend-expert 협업 전제 (사용자는 프론트 비전문).

**근거**: 서비스의 신뢰 원천인 "등급 근거 투명성"(F4)은 화면 없이는 전달 불가 — 조회 2화면(디렉토리/상세)은 양보 불가 코어. 제출/상태 2화면은 F1 수용 기준의 사용자 경험 완성 요소이나, 백엔드 API 가 선행 완성되므로 축소해도 서비스 성립.

**트레이드오프 (수용함)**: 4화면은 M4(2~3주)의 최대 변수 — frontend-expert 위임으로 백엔드 1인 부하와 분리하되, API 명세 협의 비용은 발생. 축소 발동 시 제출자 UX 저하는 추적 토큰 URL(F1)의 JSON 응답으로 최소한 보전.

**구현 함의**:
- M4 착수 시점에 **F1/F3/F4 API 명세 동결** 필요 — 백엔드가 명세를 먼저 확정하고 frontend-expert 에 전달하는 순서.
- 기존 `frontend/`(Next.js 16 스캐폴딩) 활용. 서버 컴포넌트 기본 원칙 등은 frontend-expert 영역.

## 4. 다음 단계 — DB 스키마 설계 착수 조건 충족 선언

**스키마에 영향을 주는 기획 결정이 전부 확정되었다.** 잔여 질문 #4·#5·#7·#9·#10 은 스키마 비차단 (이력 보존 구조·설정값 외부화·라벨 필드로 흡수 가능). 이에 **db-architect 의 DB 스키마 설계(ERD + Flyway 마이그레이션) 착수 조건 충족을 선언**한다.

db-architect 전달 요구사항 (기획 관점 — 설계 자체는 db-architect 영역):
1. **핵심 엔티티**: 도구(등록 repo), 제출, 분석 결과(축별 점수 + 근거), 등급 이력, Outbox (2nd_plan M1 정의).
2. **버전 3종 기록**: 모든 등급 레코드에 분석기/프롬프트/모델 버전 (결정 #1·#2, 가드레일 #3).
3. **LLM 결과 캐시**: (commit hash, 분석기 버전, 프롬프트 버전, 모델 ID) 4-튜플 키 (가드레일 #2).
4. **운영 설정값 저장**: rate limit 수치, 전역 상한, repo 크기/파일 수 상한, LLM 월 예산 — 코드 배포 없이 조정 가능 구조 (결정 #3·#6, #2).
5. **LLM 예산 카운터**: 월 누적 비용 집계 (결정 #2).
6. **상태 추적**: 제출 상태 전이 기록 (F1/F2), "LLM 보정 미적용"·"구버전 분석" 라벨 표현.
7. **등급 이력 보존**: 재제출 시 이전 등급 유지 (F2) — 잔여 질문 #4(재분석)·#9(재캘리브레이션) 대비 확장 여지.

후속 순서: db-architect 스키마 설계 → backend-expert M1 착수 (제출 API + rate limit + 안전 취득 1단계 + 통짜 관통).
