## 1. 배경 / 도메인 전환 선언

### 1.1 무엇이 바뀌나
기존 AgentGrid는 "AI 에이전트·MCP 서버의 시스템 신뢰성을 정적 분석해 A~F 등급을 주는 개발자용 레지스트리 플랫폼"이었다. 이 도메인은 **전면 폐기**하고, 동일 레포에서 **개인 1인용 한국 주식 주가 분석 프로그램**으로 전환한다.

전환의 동기: 레지스트리 플랫폼은 (1) 멀티유저·외부 repo 스크래핑·LLM 인젝션 등 보안 표면이 넓고, (2) 1인 개발 대비 운영 부담이 크며, (3) 실사용자가 본인 1명일 때 가치가 본인에게 직접 닿지 않았다. 반면 주가 분석 프로그램은 본인이 곧 사용자이자 검증자이므로 피드백 루프가 짧고, 1인 개발 규모에 맞는다.

### 1.2 버리는 것 (Discard)
- **Backend (Java / Spring Boot 4.1)** — 도메인 로직 전량 폐기, 스택 자체 교체
- **Frontend (Next.js mock 4화면)** — MCP 디렉토리/제출/상태추적 mock 폐기
- **레지스트리 기획 일체** — 하이브리드 등급 산출, 수동 등록 파이프라인, 캘리브레이션 동결, LLM 평가(sonnet-4-6), 격리 2단계, rate limit, 풀 4화면 — 전부 무효
- **인프라 중 RabbitMQ / Transactional Outbox** — 외부 스크래핑·헬스체크 비동기 파이프라인 전제였으므로 **재검토 대상**(주가 배치 수집에 MQ가 필요한지는 미해결 질문으로 이월)
- **메모리/ADR 중 위 도메인 컨텍스트** — 메인이 정리

### 1.3 유지하는 것 (Keep)
- **하네스 골격** — `.claude/`(훅 9종·rules·skills·agents·settings), drift 강제, work-history 규약, verify-commit-msg 등 **그대로 유지**. 스택 박힌 부분(backend-conventions의 Java 전제, frontend-conventions의 Next 전제)만 후속 교체.

- **인프라 중 PostgreSQL / Redis** — 시계열·캐싱 후보로 잔존(단 시계열 DB 선택은 미해결 질문)
- **1인 개발·정확성 우선·실측 기반** 작업 원칙

## 2. 목표 / 비목표

### 2.1 목표 (Goals)
1. **30년 장기 데이터 기반 정량 룰**로 코스피·코스닥 각각 **Top20** 종목을 자동 생성한다.
2. 생성된 Top20을 **사용자가 Claude 세션에서 직접 토의**(수동)해 **Top5**로 압축·정립한다.
3. Top5에 **분산투자**한 뒤 **한 달 이상 성과를 추적**한다.
4. 추적 결과를 근거로 **룰·기준을 보정**(가중치 조정)하며 룰 버전을 관리해 **점진적으로 안정화**한다.
5. 모든 룰은 **백테스트로 검증**된 뒤에만 신뢰한다(생존편향·수정주가 함정 회피를 설계 원칙으로 박는다).

### 2.2 비목표 (Non-Goals) — 명시적 범위 제외
- ❌ **AI 자동화** — 현재 미구현. AI가 시장 데이터를 수집·분석해 Top 세팅에 자동 투입하는 것은 **미래 여지로만** 남기고 우선순위 낮음(§3-4).
- ❌ **자동매매 / 실거래 연동** — 증권사 API를 통한 주문 실행, 자동 리밸런싱 일체 비목표.
- ❌ **멀티유저 / 인증 복잡도** — 개인 1인용. 회원가입·권한·과금 없음.
- ❌ **실시간 틱·HFT** — 일봉(EOD) 기준. 분/초 단위 데이터·초단타 비목표.
- ❌ **투자 권유 서비스화 / 공개 배포** — 본인 도구. 타인 대상 신호 제공·SaaS 아님.
- ❌ **파생·해외주식** — 국내 코스피·코스닥 현물 주식만.

## 4. 핵심: Top20 정량 생성 룰 (가장 깊게)

> ⚠️ 본 절은 **후보 지표 제시까지만**이다. 확정 가중치·임계값은 **미해결 질문(§9)**이며, **백테스트(§4.4)로 검증되기 전까지 어떤 가중치도 신뢰하지 않는다.**

### 4.1 설계 원칙 (BLOCKING — 룰 구현 전 반드시 박을 것)
1. **백테스트 검증 필수** — 어떤 룰·가중치도 30년 데이터 백테스트 통과 전 실투자 반영 금지.
2. **생존편향(Survivorship Bias) 회피** — **상장폐지 종목을 데이터셋에 포함**해야 한다. 현재 상장 종목만으로 백테스트하면 수익률이 구조적으로 부풀려진다. (pykrx는 폐지 종목 종가 일부 지원, 네이버 소스는 폐지 종목 미제공 — §6·§9에서 소스 확정 필요. 출처: [pykrx issue #89](https://github.com/sharebook-kr/pykrx/issues/89))
3. **수정주가(Adjusted Price) 사용** — 액면분할·유상증자·배당 등으로 인한 가격 점프를 보정한 수정주가로 수익률을 계산해야 한다. 미보정 시 모멘텀·수익률 지표가 왜곡된다. (pykrx `get_market_ohlcv`의 `adjusted` 파라미터 등 — 출처: [pykrx README](https://github.com/sharebook-kr/pykrx))
4. **룩어헤드 바이어스 회피** — 랭킹 시점에 미래 정보(아직 공시 안 된 재무 등)를 쓰지 않는다. 재무 데이터는 공시 시차(lag)를 반영해 적용한다.
5. **거래 가능성 필터** — 유동성 없는 종목, 거래정지·관리종목·우선주·스팩 등은 후보에서 사전 제외(노이즈·체결 불가 회피).
6. **LLM의 역할 한계 명시** — Claude 세션은 Top20→Top5 **정성 보정·리스크 플래그·뉴스 맥락**에 쓰이며, **알파(초과수익)의 소스가 아니다.** 알파는 백테스트로 검증된 정량 룰에서 나온다.

### 4.2 후보 지표 (Factor Candidates)
> 한국 시장 실측 참고: **사이즈·밸류 팩터가 프리미엄이 크고, 모멘텀은 미국 대비 약하거나 비유의한 경우 존재**. 멀티팩터(모멘텀+밸류) 결합이 유의미한 초과수익을 낸 연구 다수. (출처: [리스크 팩터와 퀀트 투자](https://brunch.co.kr/@quantdaddy/9))

| 그룹 | 후보 지표 | 의미 / 산출 메모 | 비고 |
|---|---|---|---|
| 모멘텀 | N개월 누적 수익률(예: 3·6·12개월), 최근 1개월 제외 모멘텀 | 상대 모멘텀 랭킹. 1개월 제외(reversal 회피)는 표준 관행 | 한국은 약할 수 있음 → 가중치 신중 |
| 추세 | 이동평균 정렬(예: 20>60>120일), 52주 신고가 근접도 | 정배열·신고가 근접은 추세 강도 프록시 | 단독보다 필터로 |
| 밸류 | PER, PBR, (가능 시 EV/EBITDA) | 저평가 랭킹. OpenDART 재무 필요 | 한국에서 프리미엄 큼 |
| 퀄리티 | ROE, 부채비율, 영업이익 안정성 | 펀더멘털 건전성. 재무 데이터 의존 | 데이터 확보 난이도 변수 |
| 사이즈 | 시가총액 | 소형주 프리미엄(단, 유동성·거래 가능성과 상충) | 유동성 필터와 균형 |
| 유동성 | 평균 거래대금(N일), 거래량 | 체결 가능성·노이즈 필터. 하한 컷오프로도 사용 | **필수 필터** |
| 리스크 | 변동성(N일 표준편차), 최대낙폭(MDD), 베타 | 저변동성 효과 + 리스크 캡 | 저위험 효과 활용 |

### 4.3 랭킹 산출 방식 (후보 — 확정은 §9)
- **방식 A — 단순 가중합 점수**: 각 지표를 횡단면 정규화(z-score 또는 퍼센타일) → 가중 평균 → 상위 20.
- **방식 B — 멀티팩터 순위 합산**: 각 팩터별 순위를 매겨 순위 합이 낮은 순(마법공식류).
- **방식 C — 필터 후 랭킹**: 유동성·거래 가능성·관리종목 등 하드 필터로 모집단을 거른 뒤, 핵심 팩터(예: 밸류+모멘텀)로만 랭킹.
- 시장 분리: **코스피 / 코스닥 각각 별도 랭킹**(시총·유동성 분포가 달라 통합 시 코스피 편중 우려).

→ 어떤 지표 조합·가중치·정규화 방식이 30년 백테스트에서 위험조정 수익(샤프 등)을 극대화하는지는 **실험으로 결정**한다(§9-2).

### 4.4 백테스트 검증 (설계 원칙 §4.1을 실행으로)
- **목적**: 룰이 과거에 작동했는지, 과적합인지 판별. 통과 못 한 룰은 실투자 미반영.
- **평가 지표 후보**: CAGR, 샤프/소르티노, MDD, 승률, 회전율, 벤치마크(KOSPI/KOSDAQ) 대비 초과수익.
- **검증 디자인 후보**: 워크포워드(walk-forward), in-sample/out-of-sample 분리, 거래비용·슬리피지·세금 반영.
- **프레임워크 후보(미해결 §9-3)**: `vectorbt`(벡터화·대량 빠름), `backtrader`(이벤트 드리븐·현실적 체결), 또는 자체 구현(pandas). 1인 규모·룰 단순도를 고려해 선택. (출처: [VectorBT/Zipline/Backtrader 비교](https://medium.com/@trading.dude/battle-tested-backtesters-comparing-vectorbt-zipline-and-backtrader-for-financial-strategy-dee33d33a9e0))

## 5. 추적 · 보정 루프

### 5.1 루프 정의
```
[30년 데이터] → (정량 룰 vN) → Top20(코스피/코스닥)
   → (Claude 세션 수동 토의) → Top5 정립
   → 분산투자 → 1개월+ 성과 추적
   → 월 단위 재평가 → 룰 가중치 보정 → 룰 vN+1
```

### 5.2 추적 (Tracking)
- Top5 편입 시점·비중·진입가 기록 → 보유 기간 수익률·MDD·벤치마크 대비 추적.
- **룰 추천 성과 vs 실제 보유 성과**를 분리 기록(수동 보정이 가치를 더했는지 측정).

### 5.3 보정 (Calibration) & 룰 버전 관리
- **룰 변경 이력 전량 보존** — 어떤 가중치를 언제·왜 바꿨고, 직전 버전 대비 추적 성과가 어땠는지. (work-history 규약과 정합)
- **월 단위 재평가**가 기본 주기 후보(§9-6). 잦은 변경은 과적합·노이즈 추종 위험.
- 보정은 **백테스트 재검증 동반** — 새 가중치도 §4.4를 통과해야 채택.

### 5.4 협업 지점
- 룰 버전·추적 데이터의 **스키마·이력 테이블 설계 → db-architect**
- 백테스트 엔진·랭킹 파이프라인 **구현 → python-expert**

> ⚠️ **구체 소스/API 선정은 tech-researcher가 병렬 조사 중** → 확정은 §9-1로 이월. 본 절은 **무엇이 필요한가**만 정의.

|---|---|---|
| **종목 마스터** | 코스피/코스닥 종목 코드·명·시장 구분·섹터 | KRX / pykrx |
| **30년 일봉 OHLCV** | 모멘텀·추세·변동성·백테스트 | pykrx(KRX·네이버 스크래핑) 등 — 30년 전 구간 커버리지·결측 검증 필요 |

| **재무 데이터(PER/PBR/ROE 등)** | 밸류·퀄리티 팩터 | OpenDART API 등. 공시 시차 반영 필요(§4.1-4) |

| **벤치마크 지수(KOSPI/KOSDAQ)** | 초과수익 평가 | pykrx 지수 데이터 |
| **(선택) 시총·상장주식수** | 사이즈 팩터·시총 가중 | 수정주가 정합 주의 |

## 7. 웹앱 범위 (PWA / 반응형 웹)

> 1인 사용 + 모바일 체감. 화면은 **후보**이며 MVP는 핵심부터(§8).

| 화면 | 내용 | 우선순위 |
|---|---|---|
| **Top20 뷰** | 코스피/코스닥 각 Top20, 종목별 팩터 점수·랭킹 근거 | Must |
| **Top5 뷰** | 수동 정립된 Top5, 선정 메모(Claude 토의 요약) | Must |
| **분산투자 현황·수익률** | 보유 비중·진입가·현재 수익률·벤치마크 대비 | Must |
| **추적 기록** | 기간별 성과 추이, 룰 추천 vs 실제 보유 비교 | Should |
| **룰 버전 / 백테스트 결과 뷰** | 룰 vN 가중치, 백테스트 지표(CAGR·샤프·MDD), 버전 비교 | Should |
| **데이터 수집 상태** | 마지막 갱신 시각, 결측·에러 | Could |

- **PWA**: 오프라인 캐시·홈 화면 추가·반응형. 네이티브 푸시·백그라운드 동기화는 비목표.
- 협업 지점: 화면 구성·상태관리 **→ frontend-expert(웹앱)**. API 계약 **→ python-expert ↔ frontend-expert**.

## 8. MVP 마일스톤 (1인 개발 현실성 검증)

> 백엔드(Python) 1인 기준. 각 단계는 **이전 단계 완료 확인 후** 진행(작업 원칙). 데이터 품질이 전 단계의 전제이므로 M1을 서두르지 않는다.

| M | 단계 | 산출물 | 완료 기준(수용 기준) | 현실성 메모 |
|---|---|---|---|---|
| **M0** | 레포 청소·스택 전환 | 레지스트리 잔재 제거, Python 프로젝트 골격, 하네스 rules 스택 교체 | 빌드·하네스 훅 통과, work-history 엔트리 | 하네스 유지가 핵심. 신규 아님 |
| **M1** | 데이터 수집·저장 | 종목마스터·30년 일봉·수정주가·(가능 시)폐지종목·재무 적재 | 코스피/코스닥 전 종목 일봉 적재, **결측·생존편향 점검 리포트** | **가장 리스크 큼**. 소스 미확정(§9-1)이 선행 |
| **M2** | Top20 룰 + 백테스트 | 랭킹 파이프라인 + 백테스트 엔진, 룰 v1 | 코스피/코스닥 Top20 산출, 30년 백테스트 지표 출력, 생존편향·수정주가 반영 검증 | 룰 단순화로 범위 통제. 과적합 경계 |
| **M3** | Top5 워크플로 + 추적 | Top20→Top5 수동 입력·메모, 보유·수익률 추적, 룰 버전 이력 | Top5 등록→일별 성과 추적→월 재평가 1회 동작 | 수동 단계는 가볍게 |
| **M4** | 웹앱 뷰 | PWA로 Top20/Top5/현황/추적/룰 뷰 | Must 화면 3종 동작, 반응형·홈화면 추가 | API 안정화 후 착수 |

> 마일스톤 순서 강제: **M1(데이터 신뢰성) 통과 없이 M2 백테스트 시작 금지** — 오염된 데이터 위에 세운 룰은 무의미.

## 10. 투자 리스크 고지 (BLOCKING — 본인용이라도 명시)

1. **백테스트 ≠ 미래 수익.** 과거 성과는 미래를 보장하지 않는다. 검증 통과 룰도 실패할 수 있다.
2. **과적합 경고.** 30년 데이터에 맞춰 가중치를 과도하게 튜닝하면 과거에만 좋은 룰이 된다. out-of-sample 검증·단순성 유지가 방어책.
3. **생존편향·수정주가 미처리 시 수익률이 구조적으로 부풀려진다.** §4.1을 위반한 백테스트 결과는 신뢰 금지.
4. **LLM(Claude 세션)의 한계.** Top5 토의는 정성 보정·리스크 플래그용이며 **알파 소스가 아니다.** LLM 환각·최신성 한계를 감안하고, 정량 근거 없는 종목 편입 금지.
5. **본인 책임.** 본 프로그램은 투자 조언이 아니며 모든 투자 판단·손익은 사용자 본인 책임이다. 실투자 전 충분한 백테스트·소액 검증을 거친다.
