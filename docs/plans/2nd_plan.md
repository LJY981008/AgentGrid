# [2차 기획안] Agent Grid — MVP 구체화: 신뢰성 지표·분석 파이프라인·기능 명세

> 작성일: 2026-06-12 | 상태: 초안 | 선행 문서: [1st_plan.md](1st_plan.md), [PLAN_STATUS.md](PLAN_STATUS.md)
> 본 문서는 1차 기획안의 비전·기술 스택(Java 21 / Spring Boot 3.x, PostgreSQL, Redis, RabbitMQ, Transactional Outbox)을 변경 없이 계승하고, 미해결 질문 5건 중 4건의 사용자 확정 결정을 반영해 MVP 를 구체화한다.

## 1. 배경 / 문제 정의

### 1.1 1차 기획안 요약
- **문제**: AI 에이전트/MCP 생태계의 폭발적 성장에 비해, 공개된 MCP 서버·플러그인 대다수가 검증되지 않은 스크립트 수준. 프로덕션 투입 가능 여부(예외 처리, 타임아웃, 재시도 등 시스템 견고성)를 판단할 정보가 없음.
- **비전**: 단순 큐레이션을 넘어 **신뢰성(Reliability)을 정량 평가(A~F 등급)하여 제공하는 개발자 중심 레지스트리**.
- **기술 스택**: Java 21 / Spring Boot 3.x + PostgreSQL + Redis + RabbitMQ, 데이터 정합성은 Transactional Outbox 패턴.

### 1.2 이번 구체화의 목적
1차 기획안은 "무엇을 만들 것인가"를 정의했으나, **"신뢰성 등급을 무엇으로 어떻게 산출하는가"** 가 비어 있었다. 등급 산출 로직은 이 서비스의 존재 이유이자 신뢰의 원천이다. 본 문서는 ① 평가 축과 탐지 규칙, ② 등급 합산식 초안과 LLM 보정 가드레일, ③ 이를 구동하는 MVP 기능 명세와 백엔드 1인 개발 기준 마일스톤을 확정 가능한 수준까지 구체화한다.

## 2. 목표 / 비목표

### 2.1 목표 (MVP)
- 개발자가 GitHub repo URL 을 제출하면, 자동 분석을 거쳐 **A~F 신뢰성 등급과 산출 근거**가 공개 디렉토리에 게시된다.
- 비로그인 사용자가 디렉토리를 **검색·카테고리 탐색·등급 조회** 할 수 있다.
- 등급 산출 과정이 **투명**하다: 축별 점수, 발동 규칙, LLM 보정 사유, 분석기 버전을 상세 페이지에 노출.
- 분석 파이프라인이 **유실 없이** 동작한다 (Transactional Outbox + 재시도 + DLQ).

## 4. 신뢰성 지표 정의 (핵심)

### 4.1 설계 원칙
1. **규칙 축은 "정적으로 실제 탐지 가능한 것"만** 채택한다. 탐지 신뢰도가 낮은 항목(멱등성 등)은 등급에서 제외하고 참고 정보로 강등한다.
2. **존재 여부가 아니라 적용률**로 점수화한다 (예: "타임아웃 코드가 있다"가 아니라 "외부 호출 지점 중 몇 %에 타임아웃이 걸려 있는가").
3. **치명 위반은 등급 상한(cap)** 으로 처리한다 — 가중 평균에 묻히지 않게.
4. 모든 점수는 **근거(규칙 ID + 파일/라인)** 와 함께 저장·공개한다.

### 4.2 평가 축 선별 결과
채택 6축 + 제외 2항목:

| 축 | 가중치(초안) | 규칙/LLM 분담 |
|---|---|---|
| R1 예외 처리 | 25 | 규칙 탐지 + LLM 품질 보정 |
| R2 타임아웃 | 20 | 규칙 탐지 위주 |
| R3 재시도/백오프 | 15 | 규칙 탐지 + LLM 적절성 보정 |
| R4 입력 검증 | 15 | 규칙 탐지 위주 |
| R5 의존성 건전성 | 15 | 규칙 전용 (LLM 개입 없음) |
| R6 문서·메타데이터 품질 | 10 | 규칙(구조 검사) + LLM(정합성 판단) |
| (제외) 멱등성 | — | 정적 규칙으로 신뢰성 있는 판별 불가에 가까움(약한 시그널: idempotency-key 헤더, upsert 패턴 정도). LLM 참고 코멘트로만 표시, 점수 미반영 |
| (제외) 서킷 브레이커 | — | 라이브러리 사용(opossum, cockatiel, pybreaker 등)은 탐지 가능하나 MCP 서버에서 희소 → 축이 아닌 **보너스(+3, 총점 상한 100)** 로만 반영 |

> 가중치 수치는 초안이며 시드 데이터 분석 결과로 캘리브레이션 후 확정 (미해결 질문 #1).

### 4.3 축별 탐지·점수화 정의

각 축은 0~100점. "호출 지점(call site)"은 AST 기반으로 식별한다 (파서 선정 등 구현 방식은 backend-expert 협업 지점).

**R1. 예외 처리 (가중치 25)**
- 탐지 (TS): I/O·외부 호출(fetch/axios/fs/DB 클라이언트)을 감싸는 try/catch 또는 `.catch()` 존재. 빈 catch 블록, catch 후 무시 패턴.
- 탐지 (Python): try/except 의 **구체 예외 vs bare `except:` / 광역 `except Exception`**, `except: pass` (silent swallow), 핸들러 내 로깅/재던지기 여부.
- 점수: `(예외 처리된 I/O 지점 / 전체 I/O 지점) × 100`, 감점 — bare except 건당 -10, 빈 catch 건당 -10 (하한 0).
- LLM 보정 대상: "catch 는 있으나 에러를 삼키고 정상 응답을 반환" 같은 형식적 처리 식별.

**R2. 타임아웃 (가중치 20)**
- 탐지 (TS): fetch 의 `signal: AbortSignal.timeout(...)` / `AbortController` 전달, axios `timeout` 옵션, node `http.request` timeout, `Promise.race` + 타이머(약한 시그널, 0.5 가중).
- 탐지 (Python): `requests.*(..., timeout=)`, `httpx.Timeout`/클라이언트 timeout 인자, `aiohttp.ClientTimeout`, `asyncio.wait_for`, `socket.settimeout`.
- 점수: `(타임아웃 설정된 외부 네트워크 호출 / 전체 외부 네트워크 호출) × 100`.
- **치명 위반 cap**: 외부 네트워크 호출이 존재하는데 타임아웃이 0건이면 최종 등급 상한 C.

**R3. 재시도/백오프 (가중치 15)**
- 탐지 (TS): p-retry, async-retry, axios-retry, cockatiel 등 import + 적용. 커스텀: 루프 내 재호출 + 지수 증가 delay 패턴.
- 탐지 (Python): tenacity/backoff 데코레이터, urllib3 `Retry`, 커스텀 루프 패턴.
- 점수: 재시도 없음 = 50(중립 — 재시도가 항상 정답은 아님), 백오프+최대횟수를 갖춘 재시도 = 100, **무한/고정간격 재시도(retry storm 위험) = 20**.
- LLM 보정 대상: 비멱등 성격 연산에 무분별한 재시도가 적용됐는지.

**R4. 입력 검증 (가중치 15)**
- 탐지 (TS): MCP tool 등록 시 inputSchema(JSON Schema) 정의 여부, zod/ajv/valibot 사용. 스키마에 타입 외 제약(required, enum, min/max, pattern) 존재 여부.
- 탐지 (Python): pydantic 모델, FastMCP 타입 힌트 시그니처, jsonschema 검증 호출.
- 점수: `(스키마 검증되는 tool 수 / 노출 tool 수) × 70 + 제약 충실도(타입만 = 0, 제약 포함 = 30)`.

**R5. 의존성 건전성 (가중치 15) — 규칙 전용**
- 탐지: lockfile 존재(package-lock/pnpm-lock/yarn.lock, uv.lock/poetry.lock/고정 requirements), 버전 와일드카드(`*`, `latest`), 알려진 취약점(OSV 데이터 대조), deprecated 패키지.
- 점수: lockfile 40 + 버전 고정율 30 + 취약점 무결 30 (high 이상 취약점 건당 -15).
- 전 항목 기계 판정 가능하므로 LLM 개입 없음.

**R6. 문서·메타데이터 품질 (가중치 10)**
- 탐지(규칙): README 존재 및 필수 섹션(설치/설정/tool 목록/환경변수), LICENSE 파일, tool description 존재율·길이, MCP 매니페스트 완결성.
- LLM 분담: "문서가 실제 노출 tool 과 일치하는가" 정합성 판단 (이 축 내 최대 ±20점).

### 4.4 등급 합산식 초안 + LLM 보정 가드레일

```
base  = Σ(축 점수 × 가중치) / 100              # 0~100
bonus = 서킷 브레이커 탐지 시 +3 (상한 100)
final = clamp(base + bonus + llm_adj, 0, 100)  # llm_adj ∈ [-10, +10]
cap   = 치명 위반 시 등급 상한 적용 (예: R2 cap → 최대 C)

등급: A ≥ 85 | B 70~84 | C 55~69 | D 40~54 | F < 40   (경계값은 초안)
```

**LLM 보정 가드레일 (필수 준수):**
1. **보정 범위 제한**: llm_adj 는 ±10점, 등급 기준 **최대 1단계**까지만 이동 가능. 등급의 뼈대는 항상 규칙 점수.
2. **일관성 — 동일 입력 동일 등급**: (repo commit hash, 분석기 버전, 프롬프트 버전, 모델 ID) 4-튜플을 키로 결과를 영구 저장·재사용. 동일 키 재호출 금지(캐시 강제). 생성 파라미터는 결정성 최대화 설정(temperature 0 등).
3. **프롬프트 버전 관리**: 보정 프롬프트는 코드와 함께 버저닝(semver)하고, 모든 등급 레코드에 프롬프트/모델/분석기 버전을 기록. 버전 변경 시 기존 등급은 무효화 대신 "구버전 분석" 라벨링.
4. **근거 강제**: LLM 은 보정 점수와 함께 **파일/라인 인용 근거**를 구조화 출력으로 반환해야 하며, 근거 없는 보정은 미적용 처리.
5. **자동 분석 한계 고지**: 모든 등급 표시 영역에 "정적 자동 분석 결과이며 실제 운영 품질을 보장하지 않음" 고지 + 분석 일시/버전 병기 (PLAN_STATUS 미해결 질문 #5 대응).
6. **실패 격리**: LLM 호출 실패/타임아웃 시 규칙 점수만으로 등급을 산출하고 "LLM 보정 미적용" 라벨 표시 — 파이프라인 전체를 블로킹하지 않음.

## 5. MVP 기능 명세 (사용자 스토리 + 수용 기준)

### F1. 도구 제출 폼
> 개발자로서, 내 MCP 서버의 GitHub URL 을 제출하여 신뢰성 등급을 받아 디렉토리에 게시되게 하고 싶다.

수용 기준:
- [ ] 비로그인 제출 가능. 입력: GitHub repo URL(필수), 연락 이메일(선택), 카테고리 제안(선택).
- [ ] URL 형식·존재(공개 repo) 검증. 비공개/404 는 즉시 거부 메시지.
- [ ] 중복 제출 시 신규 분석을 만들지 않고 기존 상세 페이지로 안내.
- [ ] 제출 직후 추적 토큰(URL) 발급 → 상태 페이지에서 `접수 → 분석중 → 게시/실패(사유)` 확인 가능.
- [ ] IP 기반 rate limit 적용 (스팸 방지 상세 정책은 미해결 질문 #6).

### F2. 분석 파이프라인
> 운영자로서, 제출된 repo 가 유실 없이 분석되고 실패가 추적되기를 원한다.

흐름: `제출 저장 + Outbox 이벤트 기록(동일 트랜잭션)` → RabbitMQ 발행 → 워커: shallow clone → 언어 판별(TS/Python 외 거부) → 규칙 분석 → LLM 보정 → 등급 산출·저장 → 상태 갱신.

수용 기준:
- [ ] 제출 레코드와 분석 시작 이벤트가 **Transactional Outbox** 로 원자적 기록 (메시지 유실 0).
- [ ] 각 단계의 상태 전이가 DB 에 기록되어 실패 지점 추적 가능.
- [ ] 단계 실패 시 제한 재시도 후 DLQ 격리, 제출자 상태 페이지에 실패 사유 표시.
- [ ] 안전 한도: repo 크기 상한(수치는 운영 조정), clone/분석 단계별 타임아웃, **클론한 코드는 절대 실행하지 않음(정적 분석만)**. 격리 수준은 미해결 질문 #3.
- [ ] 동일 repo 재제출 시 최신 commit 기준 재분석, 이전 등급 이력 보존.
- 워커 구조·큐 토폴로지·AST 파서 선정 등 구현 설계는 backend-expert 협업 지점.

### F3. 디렉토리 / 검색 / 카테고리
> 에이전트를 도입하려는 개발자로서, 카테고리와 등급으로 필터링해 신뢰할 수 있는 도구를 찾고 싶다.

수용 기준:
- [ ] 비로그인 목록 조회: 이름/설명/등급/카테고리/최근 분석일 표시, 등급·카테고리 필터, 키워드 검색.
- [ ] 정렬: 최신 등록순/등급순 (인기순은 조회수 집계가 필요 — Phase 2).
- [ ] 메인 디렉토리 응답은 Redis 캐싱, 등급 갱신 시 무효화.
- [ ] 카테고리 1차 체계는 1차 기획안 기준(DB 연동/API 연동/브라우저 제어 + 기타)으로 운영자가 부여 — 확장 체계는 미해결 질문 #5.
- 검색 구현(PostgreSQL FTS vs 외부 엔진)과 인덱스 설계는 db-architect 협업 지점.

### F4. 도구 상세 (등급 산출 근거 — 투명성)
> 등급을 본 개발자로서, 왜 이 등급인지 근거를 확인하고 싶다.

수용 기준:
- [ ] 최종 등급 + 축별(R1~R6) 점수 표시.
- [ ] 축별 탐지 근거: 발동 규칙 ID, 대표 파일/라인 예시, 적용률 수치.
- [ ] LLM 보정값과 보정 사유(인용 근거 포함), 미적용 시 그 사실 표시.
- [ ] 분석기/프롬프트/모델 버전, 분석 대상 commit hash, 분석 일시 표기.
- [ ] 자동 분석 한계 고지문 + 피드백/이의 제기 연락 채널(이메일 또는 GitHub Issue 링크).

## 6. 우선순위 (MoSCoW)

| 구분 | 항목 |
|---|---|
| **Must** | F2 분석 파이프라인(Outbox 포함), 규칙 분석기 R1~R5 (TS+Python), 등급 합산식·cap, F1 제출 폼, F3 목록/필터, F4 상세(근거 표시), 자동 분석 한계 고지 |
| **Should** | LLM 보정(R1/R3/R6) — 가드레일 #6(실패 격리) 덕에 규칙 점수만으로도 출시 가능, R6 문서 품질 축, Redis 캐싱, 제출 상태 추적 페이지 |
| **Could** | 서킷 브레이커 보너스 탐지, 멱등성 LLM 참고 코멘트, 등급 이력 표시, 키워드 검색 고도화 |
| **Won't (MVP)** | 크롤링/레지스트리 연동, 로그인/리뷰, 샌드박스/동적 분석, TS·Python 외 언어, 자동 재분석 스케줄러, 이의 제기 공식 워크플로 |

> LLM 보정을 Should 로 둔 이유: 하이브리드는 확정 방향이지만, 실패 격리 설계에 의해 규칙 전용 등급으로도 서비스가 성립하므로 출시 블로커가 아니다. 확정 결정 #1 과 모순되지 않으며 출시 순서의 문제일 뿐이다.

## 7. 마일스톤 (백엔드 1인 개발 기준 — 1차 기획안 M1~4 재정의)

| | 기간(목표) | 범위 | 1인 감당 가능성 검증 |
|---|---|---|---|
| **M1. 골격** | 2주 | 요구사항 동결, DB 스키마(도구/제출/분석결과/등급이력/Outbox — db-architect 협업), F1 제출 API + 상태 추적, 수동 트리거로 "clone → 더미 등급" 통짜 흐름 1회 관통 | CRUD + 스키마 중심, 분석 로직 없음 — 가능 |
| **M2. 파이프라인 + TS 규칙** | 3주 | RabbitMQ + Outbox 릴레이, 분석 워커 분리, 안전 한도(크기/타임아웃/비실행 원칙), **TS 규칙 분석기 R1~R5** | 규칙 분석기가 최대 리스크 — 언어를 TS 1개로 한정해 리스크 분할. 빠듯하나 가능 |
| **M3. Python 규칙 + 등급 산출** | 3주 | Python 규칙 분석기 R1~R5(M2 구조 재사용), R6, 등급 합산식·cap 구현, LLM 보정 + 가드레일(캐시/버전 기록/실패 격리) | 두 번째 언어는 패턴 재사용으로 부하 감소. LLM 연동은 보정 1종 호출로 한정 — 가능 |
| **M4. 조회면 + 출시** | 2~3주 | F3 디렉토리/검색/캐싱, F4 상세(근거 노출), 시드 데이터 10~20개 운영자 제출, 한계 고지, 배포 | 조회 API 중심 — 가능. 단 프론트엔드 작업량이 변수 (미해결 질문 #8) |

총 10~11주. 1차 기획안 M1~4 대비 변경점: "외부 오픈소스 수집 파이프라인"(구 M1)과 "주기적 헬스 체크"(구 M2)를 제거(수동 제출 결정 반영)하고, 규칙 분석기를 언어별 2개 마일스톤(M2/M3)으로 분할해 1인 개발 리스크를 평탄화했다.
