## 의도/목적 — 왜 이 작업을 하나

B-storage+파일럿(0f69a53)에서 발견된 BLOCKING: 초기 멱등 구현이 파티션 단위 purge 로 같은 거래소·연도를
공유하는 ticker 를 **조용히 소실**(AAPL/NVDA/TSLA 사라지고 MSFT만 잔존)했는데, **검증 게이트가 "현재
적재된 트리만" 보니 PASS 로 통과**(소실 미탐지)했다. 파일별 분리로 그 write 버그는 고쳤으나 **게이트
자체는 여전히 "무엇이 있어야 하는가(expected)"를 몰랐다** → S5 전체 유니버스에서 종목이 조용히 누락돼도
PASS = 생존편향 누수. 게이트가 expected vs actual 을 대조해 누락을 **시끄럽게 실패**시키도록 보강한다.

## 계획 (개요)

1. `storage.py`: write 직전 in-memory `list[DailyBar]` → `dict[ticker, TickerExpectation(row_count)]`
   포착 헬퍼 `build_expected`(0행=빈 맵, 추측 채움 금지).
2. `verify_parquet(base_dir, *, expected=None)`: DuckDB 로 ticker별 actual 행수 집계 → expected 대조.
   누락(missing)·행수미달(shortfall) = `VerificationError`(어느 ticker 가 얼마나 빠졌는지 명시).
   orphan(기대밖 적재) = 경고만. 기존 체크(중복·adj<=0·OHLC)는 유지. expected=None 이면 대조 생략(호환).
   빈 트리 + expected 있으면 전량 missing(전량 소실 = 최악 케이스) → FAIL.
3. `pilot.py`: 누적 적재이므로 i번째 적재 후 **누적 expected**(0..i ticker 행수)를 verify 에 전달.
4. 테스트: 핵심 회귀(expected={A,B,C}인데 A,B만 적재 → FAIL+C보고), shortfall, orphan(경고만 PASS),
   빈트리+expected, expected 없음(대조 생략), 그리고 pilot 누적 expected 가 소실 시뮬레이션을 잡는지.

## 비교/회고

- **의도 대비 달성도**: 게이트가 expected(기대) vs actual(실제 ticker별 행수)을 대조해 조용한 누락·
  행수미달을 시끄럽게 실패. 옛 버그 시나리오(A,B,C 중 C 소실)를 이제 잡음(음성 대조로 입증). S5 전체
  유니버스 착수 전 BLOCKING 해소.
- **설계 판단**:
  - orphan 은 `passed` 에서 제외(추가 데이터는 정합 위반 아님) — 그러나 기대와 어긋난 신호이므로 WARNING
    으로 시끄럽게 남김.
  - expected=None 기본값으로 기존 호출부 호환 유지 — 단 expected_checked=False 로 "대조 안 함"을 리포트에
    명시(옛 약점이 잔존함을 숨기지 않음). pilot 은 항상 누적 expected 전달로 강제.
  - pilot 누적 적재 특성상 단건 expected 가 아닌 **누적 expected** 가 정답(이전 ticker 소실 탐지의 핵심).
  - 빈 결과(0행) ticker 는 expected 에 넣지 않음 — 적재 no-op 이라 actual 0 과 정합(데이터 부족≠소실).
- **금융 BLOCKING 준수**: 생존편향(미확보·소실분을 PASS 로 숨기지 않고 정량 고지)·실패 명확 보고(어느
  ticker 가 기대 대비 얼마나 빠졌는지 메시지에 명시). 룩어헤드·수정주가는 이 변경 범위 밖(기존 유지).
